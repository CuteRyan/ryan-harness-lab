# Claude에게 전달하는 피드백: 규칙과 문서 작성 방식

## 결론

현재 글로벌 하네스는 규칙과 확인 절차가 너무 많아 작업을 느리게 만들고 있습니다. 문서도 결론보다 체계 설명이 앞서며, 평범한 내용을 낯선 용어로 새로 이름 붙이는 일이 많습니다.

앞으로는 **결과를 확인하는 데 필요한 최소한의 규칙만 남기고, 문서는 평범한 말로 짧게 작성해 주세요.**

## 반드시 고칠 점

### 1. 모든 작업을 절차로 만들지 마세요

- 작은 수정에 체크리스트, 승인, 에이전트 팀, 히스토리 갱신을 요구하지 마세요.
- 되돌리기 쉬운 작업은 바로 진행하고 결과만 확인하세요.
- 삭제, 배포, 외부 발송처럼 되돌리기 어려운 작업에만 강한 확인 절차를 두세요.
- 같은 내용을 규칙, 메모리, 설계 문서, 히스토리에 반복해서 적지 마세요.

### 2. 평범한 내용에 새 이름을 붙이지 마세요

설명할 수 있는 문장이라면 새로운 용어를 만들 필요가 없습니다. 특히 한국어 단어를 억지로 조합하거나 영어 표현을 어색하게 번역하지 마세요.

다음과 같은 표현은 피하거나 쉬운 말로 바꿔 주세요.

| 피할 표현 | 쉬운 표현 |
|---|---|
| 결정-박제 | 결정 내용을 문서에 기록 |
| 3축 동기화 | 관련 코드와 문서를 함께 수정 |
| 하네스 인플레이션 | 규칙이 너무 많아지는 문제 |
| 도메인 오염 | 다른 프로젝트 규칙이 섞이는 문제 |
| 프리플라이트 | 작업 전 확인 |
| 드리프트 | 내용 불일치 |
| 가드레일 | 안전장치 |
| 생명주기 관리 | 시작부터 종료까지 관리 |
| 피드백 루프 | 작업 결과 확인 |
| 컨펌 게이트 | 승인 |

새 용어를 쓰기 전에는 다음을 먼저 확인하세요.

> 평범한 문장으로 설명할 수 있는가? 그렇다면 새 이름을 만들지 않는다.

### 3. 문서를 보고서처럼 부풀리지 마세요

일반적인 작업 기록은 다음 네 가지만 있으면 충분합니다.

1. 결론
2. 바꾼 내용
3. 바꾼 이유 한두 문장
4. 확인 결과

목차, 배경, 목표, 원칙, 판단 근거, 기대 효과, 위험 분석, 변경 이력을 모든 문서에 반복해서 넣지 마세요. 상세 설명은 실제로 필요하거나 요청받았을 때만 추가하세요.

### 4. 이유를 짧게 쓰세요

결정에 이유를 남기는 것은 필요하지만, 이유를 별도 체계로 만들 필요는 없습니다.

좋은 예:

> 편집할 때마다 검사가 실행되어 느렸기 때문에, 배포와 삭제 검사만 남겼습니다.

나쁜 예:

> 이 결정을 별도 번호로 관리하고 원칙, 배경, 적용 범위, 세부 절차, 예외, 검증 단계, 관련 문서와 변경 이력으로 다시 나누는 것.

## 문서 작성 기준

- 첫 문장에 결론을 씁니다.
- 한 문단에는 한 가지 내용만 씁니다.
- 같은 말을 제목과 본문에서 반복하지 않습니다.
- 내부 작업 절차는 독자에게 필요할 때만 씁니다.
- 전문 용어가 꼭 필요하면 처음 한 번만 쉬운 뜻을 덧붙입니다.
- 새로 만든 표현보다 사람들이 평소 쓰는 말을 우선합니다.
- 짧게 쓸 수 있는 문서는 한 페이지를 넘기지 않습니다.

## 하네스 수정 기준

- 규칙은 실제로 반복된 문제를 막을 때만 추가합니다.
- 모든 호출에 실행되는 훅은 삭제, 배포, 외부 전송 등 위험한 작업으로 제한합니다.
- 일반 편집은 테스트나 최종 검토로 확인합니다.
- 체크리스트와 에이전트 팀은 필요할 때 선택해서 사용합니다.
- Claude 모델이 좋아졌다면 이전 모델의 약점을 보완하려고 만든 규칙을 다시 검토합니다.

## 완료 판단

다음 조건을 만족하면 개선된 것으로 봅니다.

- 작은 수정이 별도 승인과 체크리스트 없이 끝납니다.
- 문서를 처음 읽는 사람이 만든 용어의 뜻을 추측하지 않아도 됩니다.
- 결론과 변경 이유를 첫 화면에서 확인할 수 있습니다.
- 같은 결정이 여러 파일에 반복해서 적히지 않습니다.
- 규칙을 지키는 과정이 실제 작업보다 길어지지 않습니다.

이 피드백의 목적은 하네스를 없애는 것이 아닙니다. **도움이 되는 확인 절차만 남기고, Claude가 문제 해결과 자연스러운 설명에 집중하도록 만드는 것**입니다.
